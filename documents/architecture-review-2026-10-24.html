1 · Extract the schedule-model module: schedule_model.py

Strong

Files: storage.py → new schedule_model.py, consumed by coordinator.py, climate.py, services.py

Problem
  • Schedule semantics — mode/day mapping, node validation, active-node resolution, time math — live in storage.py (persistence file). The domain model and the disk layer share one module.
  • The same concepts are re-implemented 3×: _time_to_minutes (storage :1444, coordinator :245 nested, consumed privately by climate/coordinator, 7 private-access sites); day-carry-over (storage :1378, coordinator :706, climate :264); mode→day-bucket rules (_get_nodes_for_day :754 vs nested apply_nodes_to_schedules :1675 — inverse copies).
  • Consumers bypass public interfaces: self.storage._time_to_minutes, storage._data ×6 across climate/services/sensor. Private reach-in is the norm, not the exception.
Solution — deepen, don't just move
  • Pull the pure schedule domain into one module: validate_node, _sanitize_schedule_nodes, _normalize_schedule_mode/day (storage :37–149), apply_nodes_to_schedules (extract from :1675), _get_nodes_for_day, get_active_node*, get_next_node, time_to_minutes (delete coordinator's nested twin), day-carry-over.
  • The module owns the Node & Schedule contracts (CONTRACTS.md): one home for "what a valid node is" and "how 5/2 maps" — locality.
  • Delete the dead interpolate_temperature (:1324, zero callers).
  • storage.py keeps only persistence: load/save/migrate/group CRUD.
Deletion test

Deleting schedule_model.py wouldn't just move complexity — the triplicated minute-math and mode-mapping logic would reappear at every consumer. That's a module earning its keep.

Benefits
  • Leverage: consumers get validated node sanitization + mode mapping behind calls that already look similar; interface ≈ 8 functions, behaviour ≈ 400 lines of subtle time/day logic.
  • Locality: the mode-map rules triad (#146-class bugs, #186's 24:00 resurrection) becomes one file to fix. Triage fixes stop needing 3-file shotgun edits.
  • Test surface: already proven cheap — validate_node/_sanitize_schedule_nodes tests run with zero HA mocking today. The whole module becomes runnable in microseconds, no conftest stubs.
  • Kills the 7 private-access sites as a side effect.
Watch out
Keep it pure: importing homeassistant.const is fine, importing Store/hass re-couples it. The C7 fix (non-finite temp guard) and the C3 sanitizer belong here too, so harden once.

2 · Evict foreign systems: registry/sensor and Lovelace assets out of storage/services

Strong

Files: storage.py → entity_registry_ops.py; services.py → frontend_assets.py

Problem
  • storage.py — a persistence class — calls config_entries reload and audits the HA entity registry: _reload_sensor_platform :995, async_cleanup_derivative_sensors :1008, async_cleanup_unmonitored_storage :1091 (≈200 lines of registry work in the storage layer).
  • services.py dedupes expected-vs-registered sensor names, re-deriving the same patterns services.py :692–984 stores elsewhere — two modules must agree on a naming scheme neither owns.
  • services.py also owns the Lovelace card lifecycle: handle_reregister_card :1550 + diagnostics probe :1657 (≈300 lines, ~16% of the file) — frontend asset registration is not a schedule service.
  • Both are precisely the hard-to-test zones: hass.config_entries + aiohttp mocking.
Solution
  • entity_registry_ops.py: sensor-name derivation, cleanup passes, platform reload. Storage calls it behind one seam (on_groups_changed()); services reuses the same expected-name helpers.
  • frontend_assets.py: resource registration + reregister service + diagnostics probe (the file that would also absorb ADR-conflict fix #196's duplicate-registration loop).
  • storage.py drops to load/save/migrate/CRUD; services.py drops ~500 lines of non-service code.

3 · Frontend: extract pure logic from app.js into classic-script modules

Worth exploring

Files: frontend/app.js (7,290 ln) → several files, loaded via existing loadScript chain; no build step, ADR-001 compatible (explicitly lists this follow-up)

Problem
  • app.js is 7,290 lines with 107 top-level functions and 38 shared mutable globals (313 use-sites). Open Risks already name it: "Large-file regression risk."
  • Day/mode logic has 12+ duplicated literal sites inside app.js ('mon'..'sun' ×4, weekend pairs ×4, day-array ×4) — and it also re-implements backend storage rules. That's the Q2 review finding live at scale.
  • Latent hazard found: toggleEntityInclusion defined twice (:2628, :5219) — the later silently overrides the former.
  • Two interpolators (utils.js vs keyframe-timeline.ts) — known duplication at the seam.
Solution
  • Do the phase ADR-001 already anticipated — extract the pure clusters using the existing classic-script pattern (top-level functions become globals; panel.ts load order guarantees availability):
    1. schedule-utils.js: temp normalization (:36–115, parameterize graphSnapStep), node↔keyframe conversion (:812–980), mode/day transition pure fns (:981–1116, :4340–4385) — ≈600 lines movable with zero DOM/HA dependencies.
    2. save-queue.js: debounce/flags state as one object + its 6 functions (kills the 6-area save-flag scatter).
    3. Larger cuts (editor, event listeners, node settings) only after state threading — separate campaign.
  • Fix the double toggleEntityInclusion while touching the area.
Why not ES modules / full TS migration?

panel.ts loads scripts via classic <script> tags (utils → ha-api → app); 38 top-level lets become shared global-lexical bindings only within a single classic script. An ES-module conversion or full TS port would need to thread state through 107 functions at once — high-risk, contradicts ADR-001's "deferred" stance. Classic-script extraction keeps every step shippable and reviewable.

Benefits
  • Leverage: 14 scheduleNodesToKeyframes call sites and 10 temp-normalization sites call one tested function instead of re-deriving.
  • Mode/day transition rules (the #186/#150-class bugs and Q2 review finding) get a frontend home next to — and mirroring — schedule_model.py; the mode-map contract becomes greppable to exactly two files instead of five.
  • Extracted pure clusters unit-testable in node without a DOM.
Watch out
Load-order is now load-bearing (add new files to panel.ts's loadScripts before app.js). Keep one extraction per commit; the 38 shared globals stay in app.js until the state-object campaign.

4 · Split services.py handlers into domain registries

Speculative

Files: services.py → services/ package (schedule_services.py, profile_services.py, advance_services.py, admin_services.py) — or reject

Problem
  • services.py mixes 5 service domains (schedules, profiles/groups, advance, admin/cleanup, diagnostics) with schema tables and selector building — 1,855 lines.
  • It pokes coordinator internals: deletes coordinator.last_node_states directly at 6 sites (:996, :1034, :1099, :1483, :1519, :1536) with no cache-invalidation API on the coordinator.
Solution — but consider the smaller cut first
  • Package split is mechanical but low-leverage — interface count stays flat. Cheaper 80% win: add coordinator.invalidate_node_cache(entity_ids) and route the 6 private-access sites through it. That single deepened method removes the worst coupling without moving 1,800 lines.
  • Only do the package split when a 5th domain (e.g. #84 boost service) arrives — two adapters make the seam real.
Deletion test verdict: a services/ package mostly relocates code (complexity neither vanishes nor concentrates) → shallow split. The invalidate_node_cache method genuinely concentrates scattered knowledge → deep.

Top recommendation: Candidate 1 — schedule_model.py

Why first: lowest risk (pure functions, already partially tested), highest leverage per line moved (~800 lines in, 7 private-access lanes closed, three copies of mode/time logic replaced by one), and it is the prerequisite for doing Candidates 2 and 3 well — the registry and frontend splits both want a canonical schedule-model to point at. It also front-loads the C7 fix (non-finite temp) into its new home so the hardening ships with the seam instead of in storage.py forever.

Ordering: 1 → (2a registry, 2b frontend assets) → 3 (frontend pure extraction) → 4's small cache-invalidation cut anytime.

Ground rules noted during review

  • ADR-001 (source-of-truth frontend edits) — no candidate contradicts it; Candidate 3 executes its recorded follow-up ("phased decomposition of app.js"). No ADR conflicts surfaced.
  • Cadence reality: 3 commits on main in 6 months, solo maintainer — every split should be one shippable commit, not a branch-long migration. The pure-function extractions fit that; monolith rewrites don't.
  • Test reconciliation first: origin/feature/test-suite (~175 tests: migrations, coordinator, storage CRUD) vs local branch harness (6 tests + CI). Whichever lands first is the safety net — do that before any move.
  • Don't split what's already deep: the group/platform entities (climate.py 21KB, sensor.py 18KB, switch.py 17KB) have decent interfaces; leave them.
